# S3: Simple Storage Service

## Buckets
- "directories" to store "files"(objects)
- globally unique name
- defined at REGION level
- Naming convention
    - No uppercase, no underscores
    - 3-63 characters long
    - Not an IP
    - must start with lowercase letter or a number
    - must NOT start with prefix xn-- or end with suffic -s3alias

## Objects
All objects have a Key (path)
- s3://{bucket}/{pre/fix/}{object}
eg: s3://my-bucket/my_folder/my_subfolder/my_file.txt
- max object size: 5TB
- > 5GB files must use "multi-part upload"
- can have upto 10 tags (unicode key-val pairs)
- supports versioning

## Security
User-Based
- IAM policies - which API calls should be allowed for a specific IAM user

Resource-Based
- Bucket policies - bucket wide rules from the S3 console - allows cross account
- Object ACL - finer grained (can be disabled)
- Bucket ACL - less common

* an IAM principal can access an S3 object if
- the user IAM permissions ALLOW it OR the resource policy ALLOWS it
- AND there is no explicit DENY

Objects can be encrypted

## Versioning
**Protecting against unintended delete**
- deleting a versioned object simply creates a delete marker.
- in order to permanently delete a versioned object, you must delete the versions explicitly.

**Note**:
- Any object that existed prior to enabling versioning will have a "null" version.
- Suspended versioning does not delete previous versions.

## Replication
Cross-Region Replication (CRR)
* compliance, lower latency access, replication across accounts
Same-Region Replication (SRR)
* log aggregation, live replication across production & test accounts
must enable versioning
buckets can be in different AWS accounts
copying is async
should have proper IAM Permissions
Notes:
- after enabling replication, only NEW objects are replicated
- you can replicate existing objects (or those that failed replication ) using S3 Batch Replication

For DELETE operations
- can replicate delete markers (optional setting)
- deletions with a version ID are not replication

There is no "chaining" of replication



## Requester Pays
- in general, bucket owner pays for both storage cost as well as data transfer cost
- with Requester Pays buckets, the requester pays the cost of the request and the data transfer/download
- requester must be authenticated in AWS

## Event Notifications
- events like `S3:ObjectCreated`, `S3:ObjectRemoved` 
- supports Object name `filters` (eg: only *.jpg)
- **Example**: generate a thumbnail when an image is uploaded to S3 bucket.
- takes few seconds to a minute to deliver events
- events can be delivered to: 
    - **SNS, SQS, Lambda** (S3 needs appropriate permissions)
    - **EventBridge**s (S3 needs appropriate permissions)
      - can be sent to many more AWS Services like Kinesis, Firehose, Step Functions etc.
      - advanced filtering using JSON rules (metadata , object size, name etc)
      - archive, replay etc. (EventBridge featuress)

## Baseline performance
- 100-200ms latency
- 3500 PUT/COPY/POST/DELETE and 5500 GET/HEAD requests per second per prefix
- prefix-es are unlimited
- eg: bucker/foo/bar/file_one -> prefix=/foo/bar
- ie. If you spread your reads across 4 prefixes, you can effectively achieve 22000 read requests per second

## Performance
-Amazon S3 automatically scales about 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per prefix.

Multi-Part upload
- divide large file into parts; parallel uploads
- recommended for files > 100 MB
- must use for files > 5 GB

# S3 Transfer Acceleration
Amazon S3 Transfer Acceleration is a bucket-level feature that enables fast, easy, and secure transfers of files over long distances between your client and an S3 general purpose bucket

- files are first transferred to an AWS Edge location
- and then forwarded to destination S3 bucket via private links
- compatible with Multi-part upload
- **Note:**: Transfer Acceleration is primarily an **upload optimization** feature. For **download optimization**, use CloudFront.

S3 Byte-Range Fetches
- Parallely get specific byte ranges
- better resilience to failures
- speed up downloads
- used to retrieve partial data (head of file)

## Batch Operations
perform bulk operations on S3 objects with a single request
- modify object metadata and properties
- copy objects across buckets
- encrypt un-encrypted objects
- modify ACL tags
- restore objects from Glacier
- invoke lambda function to perform a custom operation on each object
 A Batch 'job' consists of a list of objects, the action and optional parameters
Batch Operations manages retries, tracks progress and sends completion notifications and reports
- you can use S3 Inventory --> Athena to query and filter objects

## Security
### Encryption-At-Rest
#### Server-Side:
- S3-managed Keys (SSE-S3)
    - AWS managed key
    - enabled by default
    - "x-amz-server-side-envryption":"AES256"
    
- KMS-managed Keys (SSE-KMS)
    - user controlled Keys 
    - can be audited via CloudTrail
    - "x-amz-server-side-encryption":"aws:kms"
    - "Read" requires access to Object + access to KMS
    **Limitation**: 
        - KMS API quotas-per-second are applicable. 5500/10_000/30_000 req/s based on region
    - can request a quota increase using Service Quotas console

- Customer-provided Keys (SSE-C)
    - keys managed by customer externally
    - encryption key is not stored by AWS
    - HTTPS Request + Key in header

#### Client-Side
- use client-side libraries (Amazon S3 Client-Side Encryption Library)
- clients encrypt-decrypt externally

### Encryption-In-Flight
- SSL/TLS => HTTPS
- HTTPS is recomennded
- HTTPS is mandatory for SSE-C
- a `BucketPolicy` can force Encryption-in-transit using aws:SecureTransport (set to True when using HTTPS)

### CORS
Cross-Origin Resource Sharing (CORS), is a web-browser based mechanism to allow requests to other origins while visiting the main origin
- Origin -> scheme + host (domain) + port
- eg: http://example.com/app1 & http://example.com/app2 are same Origin whereas http://www.example.com and http.other.example.com are different Origins.
- A request will not be fulfilled in this case unless the other origin allows for the requests using Access-Control-Allow-Origin CORS Headers.
- For S3 buckets with Static Website enabled, if a client makes a cross-origin request, the buckets needs to enable the correct CORS headers.
- Access-Control-Allow-Origin: http://my-origin-bucket-s3-website.us-west-2.amazonaws.com

To use MFA Delete, Versioning must be enabled
Only the bucket owner (root account) can enable/disable MFA Delete 

required for:

not required for:

uses security credentials to give a time-limited permission to download objects

- use cases:

    - allow ever-changing list of users to download files by generating URLs dynmaically
    - allow temp user to uload file to a precise location

### Glacier Vault Lock
- Write Once Read Many (WORM) model
- create a `Vault Lock Policy`
- lock the policy itself for future edits
- Usecase: Date Retention Compliance

### S3 Object Lock
- adopt a Write-Once-Read-Many (WORM) model at object level
- block an object version from being deleted or overwritten for a specified amount of time.

**NOTE:** versioning must be enabled on the Bucket

#### Retention Mode
- Compliance mode:
    - object versions cannot be overwritten or deleted by ANY user (including root)
    - retention mode cannot be changed and retention period cannot be shortened.
- Governance mode:
    - most users cannot overwrite or delete an object version or alter its lock settings
    - select users are given permissions to change retention or delete objects

#### Retention Period 
- protect the object for a fixed period of time
- can be extended

#### Legal Hold:
- protect the object indefinitely
- independant from retention period
- needs `s3:PutObjectLegalHold` IAM permission


### Access Points
provides a unique DNS endpoint for the S3 bucket that is secured by an **Access Point Policy**

- allow access from within VPC (VPC-Origin) or from the internet (Internet-Origin).
- VPC Origin:
    - needs a VPC Endpoint (Gateway or Interface Endpoint)
    - VPC Endpoint Policy must ALLOW access to the target Bucket and Access Point.

### S3 Object Lambda
use Lambda to change objects before it is retrieved by caller application
- A single S3 bucket can have an S3 Access Point and S3 Object Lambda Access Point on top of it which supports multiple use cases
- UseCases:
    - Redacting PII information from objects
    - coversion across data formats like XML to JSON etc
    - Resizing and Watermarking images on the fly using caller-specific details

# S3 Storage Classes

By default, all objects are stored in `S3 Standard (STANDARD)` storage class. You can change the storage class to optimize costs and performance based on data access patterns.

### Storage classes for frequently accessed objects (Frequent Access or FA)
#### S3 Standard (STANDARD)
This is the default storage class and provides 99.99% availability. It has low latency and high throughput.

#### S3 Express One Zone (EXPRESS_ONEZONE)
Amazon S3 Express One Zone is a high-performance, single-zone Amazon S3 storage class that is purpose-built to deliver consistent, single-digit millisecond data access for your most `latency-sensitive applications`. 

**S3 Express One Zone is the lowest latency cloud object storage class available today**, with data access speed up to 10x faster and with request costs 50 percent lower than S3 Standard. With S3 Express One Zone, your data is redundantly stored on multiple devices within a single Availability Zone.

### Storage class for automatically optimizing data with changing or unknown access patterns

#### S3 Intelligent-Tiering (INTELLIGENT_TIERING) 
is an Amazon S3 storage class that's designed to optimize storage costs by automatically moving data to the most cost-effective access tier, without performance impact or operational overhead. 

S3 Intelligent-Tiering is the ideal storage class when you want to **optimize storage costs for data that has unknown or changing access patterns.** There are no retrieval fees for S3 Intelligent-Tiering.

##### S3 Intelligent-Tiering automatically stores objects in three access tiers:

- **Frequent Access** – Objects that are uploaded or transitioned to S3 Intelligent-Tiering are automatically stored in the Frequent Access tier.

- **Infrequent Access** – S3 Intelligent-Tiering moves objects that have not been accessed in 30 consecutive days to the Infrequent Access tier.

- **Archive Instant Access** – With S3 Intelligent-Tiering, any existing objects that have not been accessed for 90 consecutive days are automatically moved to the Archive Instant Access tier.

In addition to these three tiers, S3 Intelligent-Tiering offers two optional archive access tiers:

- **Archive Access** – S3 Intelligent-Tiering provides you with the option to activate the Archive Access tier for data that can be accessed asynchronously. After activation, the Archive Access tier automatically archives objects that have not been accessed for a minimum of 90 consecutive days.

- **Deep Archive Access** – S3 Intelligent-Tiering provides you with the option to activate the Deep Archive Access tier for data that can be accessed asynchronously. After activation, the Deep Archive Access tier automatically archives objects that have not been accessed for a minimum of 180 consecutive days.


### Storage classes for infrequently accessed objects

The `S3 Standard-IA` and `S3 One Zone-IA` storage classes are designed for long-lived and infrequently accessed data but required immediate access to the data when (IA stands for infrequent access.) S3 Standard-IA and S3 One Zone-IA objects are available for millisecond access (similar to the S3 Standard storage class). Amazon S3 charges a retrieval fee for these objects, so they are most suitable for infrequently accessed data

#### S3 Standard-IA (STANDARD_IA)
Amazon S3 stores the object data redundantly across multiple geographically separated Availability Zones (similar to the S3 Standard storage class). S3 Standard-IA objects are resilient to the loss of an Availability Zone. This storage class offers greater availability and resiliency than the S3 One Zone-IA class. To help you optimize costs between S3 Standard and S3 Standard-IA you can use Amazon S3 analytics – Storage Class Analysis

#### S3 One Zone-IA (ONEZONE_IA)
Amazon S3 stores the object data in only one Availability Zone, which makes it less expensive than S3 Standard-IA. However, the data is not resilient to the physical loss of the Availability Zone resulting from disasters, such as earthquakes and floods. The S3 One Zone-IA storage class is as durable as S3 Standard-IA, but it is less available and less resilient. 


We recommend the following:

- S3 Standard-IA (STANDARD_IA) – Use for your primary or only copy of data that can't be re-created.
- S3 One Zone-IA (ONEZONE_IA) – Use if you can re-create the data if the Availability Zone fails, for object replicas when configuring S3 Cross-Region Replication (CRR). Also, for data residency and isolation, you can create directory buckets in AWS Local Zones and use the S3 One Zone-IA storage class.

Note: Both S3 Standard-IA and S3 One Zone-IA have a minimum storage duration of 30 days.


### Storage classes for rarely accessed objects

The `S3 Glacier Instant Retrieval (GLACIER_IR)`, `S3 Glacier Flexible Retrieval (GLACIER)`, and `S3 Glacier Deep Archive (DEEP_ARCHIVE)` storage classes are designed for low-cost, long-term data storage and data archiving. These storage classes require `minimum storage durations` and `retrieval fees` making them most effective for rarely accessed data.

#### S3 Glacier Instant Retrieval (GLACIER_IR)
Use for long-term data that's rarely accessed and requires milliseconds retrieval. Data in this storage class is available for real-time access. Minimum storage duration of 90 days.

`S3 Glacier Flexible Retrieval` and `S3 Glacier Deep Archive` are archival storage classes. This means that when you store an object in these storage classes that object is archived, and cannot be accessed directly. To access an archived object, you submit a restore request for it, and then wait for the service to restore the object. 

#### S3 Glacier Flexible Retrieval (GLACIER)
Use for archives where portions of the data might need to be retrieved in minutes. Data in this storage class is archived, and not available for real-time access. Minimum storage duration of 90 days and typical retrieval time of 1-5 minutes for expedited retrieval and 3-5 hours for standard retrieval.

#### S3 Glacier Deep Archive (DEEP_ARCHIVE)
Use for archiving data that rarely needs to be accessed. Data in this storage class is archived, and not available for real-time access. Minimum storage duration of 180 days and typical retrieval time of 12 hours for standard retrieval and 48 hours for bulk retrieval.
